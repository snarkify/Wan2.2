Headline: a one-line patch to wan/distributed/cfg_parallel.py (add torch.cuda.current_stream().synchronize() after dist.all_gather) drops in-tree CFG-parallel-2 from 825 s → 613 s diffusion (27%) with bit-identical output. After the fix, in-tree comes within ~14% of xDiT's wall and the external-engine cluster is the only place that can go faster — at the cost of binding to diffusers.WanPipeline's code path instead of in-tree.

Profiling framework

YAML-driven sweep harness (scripts/profiling/sweep.py) over per-config N-run driver (variance_run.py). Each run is a fresh torchrun ... generate.py process. Per-rank timing CSVs + Chrome traces written by wan/profiling/.

Default protocol: 3 runs with --skip-first (warmup discarded → n=2 measured). Winner configs hardened to n=4 or n=5. Numerical equivalence verified post-hoc with ffmpeg PSNR + SSIM and MD5 of the H264-encoded mp4 outputs.

diffusion_s is the headline metric: wall time of the 40-step denoising loop only. Excludes T5 text encoding, model load, and VAE decode. Reason: the loop is what scales with parallelism; the rest is fixed overhead independent of the configurations being compared.

Why CFG-parallel-2 beats Ulysses-2 at 2 GPUs

3300× less NCCL traffic ⇒ ~6% per-step compute savings on NVLink-connected H100s. The collective cost dominates Ulysses on 2 GPUs because the per-rank token count is so small that the all_to_all overhead exceeds the compute savings.

Key insight from Phase 1: Y0 (no-offload + Ulysses) and Y2 (FSDP + Ulysses) both OOM at 720p — the 80 GB ceiling is tight enough that activation memory + DiT weights leaves no room for FSDP's unsharded all-gather buffers (27 GB) or for both DiTs resident with activations. CFG-parallel-2 with offload (Y4) is the only path that fits comfortably and runs fastest. After the sync fix, Y4-sync stays the winner.

5. Phase 2 — xDiT (xfuser) external engine

Wrote three local xfuser adapters under scripts/profiling/ because xfuser ships the attention-processor for Wan2.x but not the transformer- or pipeline-level wrappers:

  • xfuser_wan_transformer.py — registers xFuserWanTransformer3DWrapper for diffusers' WanTransformer3DModel and xFuserWanAttentionWrapper for WanAttention (handles rotary_emb arg)
  • xfuser_wan_pipeline.py — WanXFuserPipeline for diffusers.WanPipeline; handles Wan2.2-specific dual transformer + dual guidance, also frees DiTs to CPU before VAE decode to avoid OOM
  • run_xdit.py — torchrun-launchable runner emitting stub timing_rank0.csv

Two bugs in our xDiT wrapper that masked the X1 result

Bug 1: run_xdit.py had if is_dp_last_group() and rank == 0: guarding the mp4 save. On CFG-parallel-2, is_dp_last_group() requires cfg_rank == cfg_world - 1 — which means world-rank 1, not 0. The two conditions were unsatisfiable, so no mp4 was ever saved. Fix: drop the rank == 0 constraint; the dp-last-group rank is the one that actually decoded the video.

Bug 2: After fix #1, rank 1 OOM'd at VAE decode time — 78 GB used by both DiTs + 2.64 GB scratch needed but only 1.3 GB free. Fix: move DiTs to CPU + torch.cuda.empty_cache() before VAE decode in xfuser_wan_pipeline.py. After both fixes, mp4 saves cleanly.

Note on the FA2 vs SDPA wall difference: X1 reported 763.6 s on the old server with env/attn_backend=flash_attn_2 in the timing CSV, and 539 s on the new server with SDPA fallback. The probe at runtime may have caught FA2 as importable in either case (since the package is installed both times), but at actual attention time the load path differs. Both runs are real; the new-server number is what's reproducible today.

Why X2 (USP-2) OOM'd

xfuser's standard transformer wrapper monkey-patches each block's attention processor to an SP-aware variant (xFuserWanAttnProcessor) that pre-allocates a full-sequence scratch buffer per rank. Combined with both DiTs resident (xfuser does not interleave cleanly with diffusers' --cpu-offload knob — the offload hook is installed before the SP wrapper takes effect), peak demand is roughly 83 GB on an 80 GB ceiling. The xfuser-recommended fix is layerwise offload, a considerably deeper integration than the wrapper approach we used here.

7. Phase 3 follow-on — Y4 scheduler_step regression FIX (27% win)

The visible symptom: per-span profiling showed Y4's scheduler_step running 2640× slower than Y1's (~3008 ms vs ~1.1 ms per step, accumulating to ~115 s wasted over 40 steps). The actual cause was implicit-sync pollution from cfg_all_gather's async dist.all_gather returning before NCCL completed — the next CUDA op (torch.tensor inside scheduler.step) syncs implicitly against the unsynchronized NCCL stream and pays the entire wait there.

The fix (one line)

# wan/distributed/cfg_parallel.py
def cfg_all_gather(tensor: torch.Tensor):
    contig = tensor.contiguous()
    gathered = [torch.empty_like(contig) for _ in range(_CFG_SIZE)]
    dist.all_gather(gathered, contig, group=_CFG_GROUP)
    # ↓ added 2026-05-12 — drops Y4 diffusion 27%
    torch.cuda.current_stream().synchronize()
    return gathered[0], gathered[1]

Per-span timing — before vs after the fix (new server, SDPA, same hardware)

SpanMedian per-step beforeMedian per-step after Δ
scheduler_step2830 ms1.3 ms2200× faster (regression eliminated)
cfg_all_gather0.4 ms (wall — NCCL still async)2545 ms (now includes the wait)cost correctly attributed
model_forward_cfg_split16,499 ms11,814 ms4.7 s/step saved (the unexpected win)
diffusion_loop (total)833,794 ms613,326 ms27% faster
The surprising part: the visible scheduler_step regression (~3 s) wasn't where the win came from. The real saving was in model_forward_cfg_split — 4.7 s/step × 40 steps = 188 s recovered. Without the explicit sync, the NCCL backlog after each cfg_all_gather polluted the next step's kernel launches (allocator fragmentation, sync-on-alloc cascades, etc.). The sync drains the GPU between steps so the next step's model forward queues cleanly. Lesson: "the regression you see in the profile" and "the place where time is actually being lost" can differ by an order of magnitude; trust the total wall time over per-span attribution.

8. Phase 3 follow-on — Y4 variants (no-offload, n=5)

Hypothesis to test: the 14% gap between Y4-sync (613 s) and xDiT X1 (539 s on new server) might be from Y4-sync's --offload_model True bouncing models between CPU and GPU at the boundary timestep. xDiT keeps both DiTs GPU-resident; if that's the bottleneck, dropping offload should close the gap.

Conclusion: dropping --offload_model True saves ~2 s out of 613 (within run-to-run noise) and produces MD5-identical output. Model offload is effectively free on this platform. The Y4-sync default keeps offload on for memory safety on tighter platforms.

10. Phase 3 follow-on — torch.compile mode tuning (negative result)

Y5 (default-mode compile) on the old server gave 780.6 s (2.08×) but drifted 28.4 dB from Y1. Y6 (reduce-overhead) and Y7 (max-autotune) on the old server failed with a torch CUDAGraph allocator bug — wall numbers recorded (~580 s) but no mp4 saved. On 2026-05-12, retried on torch 2.11.

Two reasons not to use compile-mode tuning:
  1. Non-deterministic. Same config, same seed, same flags, Y6 run 0 and run 1 produced different MD5s with 29 dB PSNR between them (CV 2.6%). CUDA Graphs capture varies per run, leaving the diffusion trajectory non-reproducible.
  2. Marginal speedup. Y6 mean is 592.4 s vs Y4-sync 613.2 s — only 1.8% faster, within compile-overhead noise. With non-determinism on top of ~28 dB drift vs Y4-sync, it's not worth the trade.
Y7 max-autotune is also broken on this stack: the CUDA Graphs private pool reserves 10.82 GB, leaving 5 GB free for compile scratch, and max-autotune needs 8.65 GB allocation → OOM.

Added WAN_USE_DIFFUSERS_SCHEDULER=1 env-flag in wan/text2video.py that swaps in diffusers.UniPCMultistepScheduler. Same prompt, same seed, same everything else. Result:

Scheduler is one real divergence source but not the dominant one. Swapping it moves the output away from in-tree without bringing it closer to diffusers-vanilla. The remaining divergence is in the model forward path itself: wan/modules/model.py::WanModel vs diffusers.WanTransformer3DModel are different implementations at the layer level (attention, layernorm, MLP). The "find one line" framing of the RNG-divergence task is the wrong frame — the divergence is distributed across the implementation. Closing the gap would require porting one model class to match the other, a much larger surgery. The env-flag is committed as a diagnostic tool for future investigation.

15. Key insights

  1. CFG-parallel-2 beats Ulysses-2 on 2× NVLink H100s. Trades 5 TB of all_to_all traffic per generation for one 1.5 GB all_gather. ~6% per-step compute savings; with the sync fix, that grows to ~8.8% on bit-equal output.
  2. The visible regression isn't always where the time is being lost. The 2640× scheduler_step slowdown was real, but fixing it saved 27% rather than the 14% the per-span math predicted. Implicit sync-on-allocation in the NCCL backlog also polluted subsequent model forwards. Trust total wall time over per-span attribution.
  3. Bit-equality across parallelism schemes is preserved. Y1 = Y4 = Y4-sync = Y4-no-offload = Y1-new all produce the same MD5 within a platform. Different parallelism strategies, different offload knobs, same byte-identical output. Strong correctness property.
  4. Cross-engine PSNR cluster is sample variation, not loss. Three independent diffusers-path engines (vanilla, xDiT, SGLang) all sit 14–18 dB from in-tree and ≤ 4 dB from each other. This pattern is incompatible with lossy approximation; it's the diffusers vs in-tree code path producing different valid samples. Visual A/B confirms it.
  5. Compile modes are production-unfriendly here. Beyond the ~28 dB drift on default mode, the alternate modes (reduce-overhead, max-autotune) are non-deterministic across runs — same config, same seed, different MD5s, different walls. CUDA Graphs capture is the suspect. Not worth the 1.8% marginal speedup vs Y4-sync.
  6. Model offload is free on this platform. --offload_model True on Y4-sync produces MD5-identical output and within-noise wall time vs no-offload. The CPU↔GPU bounce at the boundary timestep is fast enough not to matter. Keep offload on by default for memory safety on tighter platforms.
  7. The diffusers-vs-in-tree divergence is distributed. Scheduler implementation accounts for ~24 dB of attainable displacement but doesn't close the gap; the rest is in the model forward (different WanModel vs WanTransformer3DModel implementations). "Find one line" is the wrong frame — the gap is many lines.
  8. Findings transfer T2V → I2V cleanly. Same DiT architecture, same sync-fix behavior, same per-step rate. The production recommendation generalizes.
